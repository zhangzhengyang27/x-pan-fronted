## 产品概述

本任务为「仅方案设计」交付，不修改任何代码文件。目标是为 x-pan 网盘前端的文件预览体系产出一份可直接指导后续实施的重构方案文档，包含两大内容：

1. **格式清单**：对照现有 `resolvePreviewKind` 已覆盖的格式，梳理出「当前 unsupported、但网盘用户高频」的文件格式，按 P0/P1/P2 三级给出优先级、对应的后端 `FileType` 类型码、以及建议的渲染策略（后端转换复用 PdfPreviewer / 纯前端解析 / 原生标签）。
2. **插件化预览注册表架构设计**：把当前散落在 `resolvePreviewKind`（类型判定）和 `drive-preview-modal.vue`（渲染分发 v-if 链）的逻辑，统一收敛为可扩展的「插件注册表」模式，实现「加一种格式 = 加一个插件」的目标，同时保持向后兼容、不破坏现有预览功能。

## 核心特性

- 输出格式清单（P0/P1/P2 分级），每个格式标注后端 FileType 码、渲染策略、优先级理由
- 设计 `PreviewPlugin` 插件接口（id、match 判定、优先级、渲染组件懒加载、openInNewTab 策略、尺寸配置）
- 设计插件注册表 registry 及 `resolvePreviewKind` 的替换方式（保持向后兼容）
- 设计 drive-preview-modal 渲染分发如何从 v-if 链改为插件表驱动
- 设计 iframe 路由与 openInNewTab 的分发收敛方式
- 设计懒加载 / 代码分包策略，复用现有 `defineAsyncComponent`
- 设计对现有 ptoken 鉴权、缩略图缓存、文本编码识别的兼容方案
- 给出分阶段迁移路径，确保不破坏现有功能

## 技术栈

本任务为纯方案设计，不改代码。方案基于现有项目技术栈展开：

- **前端框架**：Vue 3 + TypeScript（组合式 API + `defineAsyncComponent` 懒加载）
- **现有预览组件**：`src/components/preview/*.vue`（pdf/video/audio/office/markdown/code/image 预览器）
- **鉴权链路**：ptoken 短期签名直链（`resolvePreviewUrl`）
- **后端类型码**：`src/types/index.ts` 的 `FileType` 枚举

## 实现方案

### 一、格式清单（当前 unsupported 但网盘高频）

对照 `resolvePreviewKind` 已覆盖的 image/video/audio/pdf/office/docx/excel/pptx/markdown/code/text，以下为建议补充的格式。

**P0（高优先级，网盘高频 + 后端已识别，落地成本低）**

| 格式 | 扩展名 | 后端 FileType | 渲染策略 | 优先级理由 |
| --- | --- | --- | --- | --- |
| 压缩包 ZIP | zip | ARCHIVE(2) | 后端解压返回目录列表 + 复用 PdfPreviewer/文本预览（或新增归档列表组件） | 后端已支持 ZIP 解压，网盘高频，`common.ts` 已有 `ARCHIVE_EXTS` |
| CSV | csv | CSV(12) | 纯前端解析（表格渲染），或复用 CodePreviewer 文本模式 | 后端已有 CSV(12) 类型码，表格数据网盘高频，前端解析成本低 |


**P1（中优先级，网盘常见但需额外解析能力）**

| 格式 | 扩展名 | 后端 FileType | 渲染策略 | 优先级理由 |
| --- | --- | --- | --- | --- |
| 压缩包 RAR/7Z/TAR/GZ/BZ2 | rar/7z/tar/gz/bz2 | ARCHIVE(2) | 后端解压（当前仅 ZIP，需后端扩展）或纯前端 JSZip（仅 zip 系，rar/7z 需 libarchive wasm） | `ARCHIVE_EXTS` 已定义但注释注明后端仅支持 ZIP |
| 思维导图 | xmind | NORMAL(1) | 纯前端解析（xmind 是 zip 结构，用 JSZip 解析 content.json 渲染） | 网盘知识管理场景常见 |
| 邮件 | eml/msg | NORMAL(1) | 纯前端解析（eml 是 MIME 文本可解析；msg 是 OLE 需 lib） | 归档场景中等频率 |


**P2（低优先级，长尾/重格式，需 WASM 或服务端转换）**

| 格式 | 扩展名 | 后端 FileType | 渲染策略 | 优先级理由 |
| --- | --- | --- | --- | --- |
| CAD | dxf/dwg | NORMAL(1) | 服务端转换或 WASM（dwg 是私有格式，需专用库） | 工程场景小众 |
| 3D 模型 | gltf/glb/obj/stl | NORMAL(1) | 原生标签不支持，需 Three.js WebGL 渲染 | 长尾 |
| 国产版式 | ofd | NORMAL(1) | 服务端转 PDF 后复用 PdfPreviewer | 政务场景 |
| GIS | geojson/kml | NORMAL(1) | 纯前端（geojson 是 JSON，可复用 CodePreviewer；kml 是 XML） | 长尾 |


**补充说明**：`geojson`、`kml` 本质是 JSON/XML 文本，其实只需把扩展名加进 `CODE_EXTS` 即可低成本覆盖，可上调至 P1。

### 二、插件化预览注册表架构设计

#### 2.1 插件接口定义

建议在 `src/utils/preview-plugin.ts`（或 `src/plugins/preview/` 目录）定义统一接口：

```typescript
// 插件唯一标识，与 PreviewKind 对齐（可扩展新 kind）
export type PreviewPluginId = string

// 单个预览插件的完整契约
export interface PreviewPlugin {
  id: PreviewPluginId
  // 判定：给定文件输入，返回是否由本插件负责（替代 if/else）
  match(input: PreviewInput): boolean
  // 优先级：多个插件同时 match 时取最高（默认 0）
  priority?: number
  // 渲染组件（懒加载工厂，复用 defineAsyncComponent）
  component: () => Promise<Component>
  // 是否走全屏浮层（如图片画廊），而非弹窗
  fullscreen?: boolean
  // 弹窗尺寸配置（替代 modalWidth/contentHeight 的 switch）
  modal?: { width: number; height: string }
  // 新窗口打开策略（替代 openInNewTab 的 if/else）
  openInNewTab?: (item: PreviewItem, url: string) => void
}
```

#### 2.2 插件注册表 registry 与 resolvePreviewKind 替换

- 新增 `registerPreviewPlugin(plugin)` 和 `resolvePreviewPlugin(input): PreviewPlugin | null`。
- `resolvePreviewKind` 改为「调用 `resolvePreviewPlugin`，命中则返回 plugin.id，未命中返回 'unsupported'」，从而**保持现有调用方（useDrivePreview.ts、iframe/index.vue）零改动**。
- 内置插件初始覆盖现有 image/video/audio/pdf/office/docx/excel/pptx/markdown/code/text，行为与现有 if/else 完全一致。
- 注册表内部按 `priority` 降序 + 注册顺序排序，`resolvePreviewPlugin` 取第一个 `match` 为 true 的插件。

#### 2.3 drive-preview-modal 渲染分发改为插件表驱动

- 移除模板中的 v-if/v-else-if 链，改为「根据 `state.kind` 查注册表拿到 plugin，用 `<component :is="plugin.component">` 动态渲染」。
- `modalWidth` / `contentHeight` 从 `plugin.modal` 读取，不再用 switch 硬编码。
- `openInNewTab` 从 `plugin.openInNewTab` 读取，未定义则走默认 iframe 路由兜底。
- 图片画廊等 `fullscreen` 插件走独立浮层分支（保留现有 ImageGalleryPreviewer 逻辑）。
- 渲染组件保持 `defineAsyncComponent` 懒加载，确保各插件代码分包。

#### 2.4 iframe 路由与 openInNewTab 分发收敛

- `src/views/preview/iframe/index.vue` 同样改为「查插件注册表 → 动态渲染组件」，替代 v-if 链。
- `openInNewTab` 的三种路由策略（流直链 / office 路由 / iframe 路由）下沉为各插件的 `openInNewTab` 默认实现，集中在一个工具函数中，避免散落。

#### 2.5 懒加载 / 代码分包策略

- 每个插件的 `component` 用 `() => import('@/components/preview/xxx.vue')` 返回，Vite 自动按 chunk 分包。
- 插件注册表文件保持轻量（只 import 类型和判定逻辑），渲染组件全部懒加载，避免首包膨胀。
- 新增重型格式（如 3D/CAD 的 WASM 库）通过插件独立 chunk 按需加载。

#### 2.6 与现有能力的兼容

- **ptoken 鉴权**：插件只负责「判定 + 渲染分发」，URL 获取仍统一走 `resolvePreviewUrl`，不改变鉴权模型。
- **缩略图缓存**：缩略图逻辑（IndexedDB + LRU）独立于插件体系，不受影响。
- **文本编码识别**：`decodeTextContent` 保持独立工具，markdown/code/text 插件复用。
- **shiki grammar 裁剪**：`resolveShikiLanguage` / `SUPPORTED_SHIKI_LANGS` 保持独立，code 插件复用。

#### 2.7 分阶段迁移路径（不破坏现有功能）

1. **阶段一**：新增 `preview-plugin.ts`，把现有 if/else 判定逻辑「平移」为内置插件，`resolvePreviewKind` 内部改为查注册表（对外签名不变）。此阶段零外部改动，纯重构验证等价性。
2. **阶段二**：把 `drive-preview-modal.vue` 的 v-if 链改为插件表驱动，逐步验证每个 kind 渲染一致。
3. **阶段三**：收敛 `openInNewTab` 和 iframe 路由分发。
4. **阶段四**：按格式清单增量注册新插件（P0 → P1 → P2），每个新格式独立验证。

### 性能与可靠性

- 插件判定 `match` 用扩展名数组 + mimeType 前缀，复杂度 O(插件数 × 扩展名数)，插件数量有限，性能无瓶颈。
- 渲染组件懒加载 + 按 chunk 分包，避免重型 WASM/WebGL 库进首包。
- 注册表支持运行时 `registerPreviewPlugin`，为后续动态扩展留口子，但默认只内置现有格式，不引入额外依赖。

## Agent Extensions

### SubAgent

- **code-explorer**
- 用途：在生成方案前，对现有预览组件（pdf/video/audio/office/markdown/code/image 各预览器的 props 契约）及 useDrivePreview、iframe 路由做一次完整梳理，确保插件接口定义（尤其是各预览器组件的 props 签名）与现有实现精确对齐，避免方案中的接口签名与真实组件不一致。
- 预期结果：产出一份各预览器组件的 props 输入/事件契约清单，作为插件接口定义的事实依据，保证方案可落地。
